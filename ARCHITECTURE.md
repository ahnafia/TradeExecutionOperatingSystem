# Distributed Trading & Portfolio Management System
## Architecture Plan v2

*Revision of v1. Every change is a resolution of a defect found in adversarial review;
§0.6 lists them. Where v1 made a claim that did not hold, this version states the
mechanism that makes it hold, or states the weaker claim honestly.*

## 0. Design thesis

> A partitioned, serialized-writer trading core with a double-entry ledger as the source of
> truth, an event log for durability and replay, and a symbol-sharded matching engine —
> such that no order is ever lost, no fill is ever applied twice, and money is provably
> conserved under crash, duplication, and partition.

Three principles drive every decision below:

1. **Serialized writer per account.** All state mutation for an account is serialized
   through a lock on that account's row, held for the duration of one Postgres
   transaction, in a process holding a valid partition lease. Concurrency is *across*
   accounts, never within one. This eliminates cross-service transactions and the entire
   class of double-spend bugs.

   > v1 said "single writer per account… by construction rather than by mechanism." That
   > was overclaimed. Correctness here comes from three concrete mechanisms — the row
   > lock, the partition lease epoch, and the database's uniqueness constraints. Naming
   > them is stronger than claiming they aren't needed. See §2.5.

2. **One durable write on the hot path.** Order acceptance is a single Postgres
   transaction. Everything downstream is driven by the event log, not by RPC success.
3. **The ledger is the truth; everything else is a projection.** Positions, balances, and
   analytics are all derived. Divergence is detectable as an arithmetic invariant, not a
   fuzzy diff.

A fourth principle, added in v2 because it turned out to be load-bearing everywhere:

4. **Every event that moves money has a deterministic identity.** `event_id` is a pure
   function of the state that produced it, never a random UUID. This is what makes crash
   recovery idempotent rather than merely hopeful. See §5.3.

## 0.5 Scope: Part 1 is the engine

The project ships in two parts. **Everything in this document is Part 1 unless marked
`[P2]`.**

| | **Part 1 — the engine** | **Part 2 — the platform** |
|---|---|---|
| Users | synthetic, generated by a load harness | real, self-registered |
| Client | CLI + scenario runner + Grafana | browser, WebSocket, thin UI |
| Identity | opaque `account_id` UUIDs | OAuth, sessions, users table |
| Book participants | simulated market makers only | real accounts + market makers |
| Deployment | local Compose + on-demand benchmark cluster | always-on public playground |
| Success | chaos block passes at 1M orders; scaling curve plotted | people use it and it stays up |

Part 1 is the part with technical substance and the part that is hard. Part 2 is a
membrane around it.

### The six seam contracts

1. **The engine knows only `account_id`.** An opaque UUID. No email, no password hash, no
   display name, no OAuth subject ever enters an engine table. Part 2 adds a separate
   `users(id, oauth_sub, email, account_id)` table in its own schema and maps inbound
   identity to `account_id` at the gateway. The engine's schema does not change.

2. **Auth is an interceptor, never handler logic.** The gateway ships a gRPC interceptor
   chain from day one. In Part 1 the auth interceptor is a no-op that trusts an
   `x-account-id` header. Part 2 replaces that one interceptor.

3. **There is never a stubbed fill path — not even in Phase 1.** Phase 1 builds a real
   price-time-priority book in-process, with one simulated market maker resting limit
   orders in it. Later phases move that book across a process boundary; they never
   *create* it. See §14.

   > v1 stated this contract and then violated it in its own Phase 1 ("immediate
   > synchronous fill"), and referred to a "Phase 1.5" that did not exist in the build
   > order. v2 fixes the plan rather than the wording: the cheapest moment to build a
   > real book is when it is a single-threaded in-memory data structure with no network
   > around it.

4. **`SubscribeFills(account_id)` exists in Part 1.** A server-streaming RPC emitting
   order lifecycle events per account. The load harness ignores it; write it anyway and
   test it. Part 2's WebSocket bridge is then a ~100-line adapter.

5. **Partition and shard counts are config, not constants.** `CORE_PARTITIONS`,
   `SYMBOL_SHARDS`, `PARTITION_WORKERS`, `BOOK_DEDUP_WINDOW`, `COLLAR_BPS`,
   `MAX_REF_PRICE_STALENESS`. Any `const N = 4` in the code is a Part 2 bug waiting to
   happen.

6. **Rate limiting has a hook, not an implementation.** A no-op interceptor slot in the
   chain.

### Part 1's demo surface

No browser. A CLI (`tradectl submit`, `tradectl positions`, `tradectl replay`), a scenario
runner driving synthetic load, and a Grafana dashboard with the invariant gauges in the
top row. The screen showing `clearing_open_delta = 0` and `share_conservation_delta = 0`
while partitions are being killed is the whole pitch.

## 0.7 Corrections from building Phase 1

Four things the document got wrong that only surfaced once the code ran. They are listed
separately from §0.6 because that table records defects found by reading; these were found
by executing, which is a different and more reliable instrument.

1. **A transaction cannot "sum to zero" across mixed units.** §3.2's original example put
   cents and share counts in one column and claimed balance. Postings balance per
   *(transaction, unit)* — see §3.1. This is not a presentational fix: the deferred
   trigger groups by unit, and without that grouping it either rejects every fill or,
   if the numbers coincidentally cancel, accepts a genuinely broken one.

2. **Fees must be charged on cumulative notional, as a delta.** Rounding each partial
   fill's fee up independently can exceed the fee headroom reserved at accept time by up
   to one minor unit per fill — which breaks "realized cost ≤ reserved", the property the
   whole no-negative-cash argument rests on. The fix is to charge
   `fee(cumulative + this) − fee(cumulative)`, which telescopes to a single rounded-up
   charge on the total no matter how the order is sliced. There is a property test for
   the identity because the failure is invisible at small scale.

3. **Cash balance needs a projection.** Deriving it by summing an account's postings makes
   the risk check O(history) — the hot path degrades continuously as the ledger grows, and
   a load test would report a throughput curve that says more about table size than about
   partitioning. `account_balances` is maintained in the same transaction as the postings,
   and comparing the two becomes one of the few genuinely non-tautological single-database
   invariants.

4. **The positions-vs-ledger check must be scoped to `POSITION` accounts.** An account's
   `CLEARING` and `EXTERNAL` legs are share-denominated too, so a naive join over all
   share-unit ledger accounts reports every counterparty leg as a mismatch. This was a bug
   in the invariant rather than in the engine — worth recording, because an invariant that
   cries wolf is worse than no invariant: the first instinct on seeing it fire is to
   distrust the checker, which is exactly the instinct that lets a real violation through.

### Found while building Phase 2

5. **The book's outputs must reach the ledger in the order the book produced them.** This
   was a real bug that destroyed shares, and the design as written did not prevent it.

   The book correctly serializes a cancel against a crossing order — one lock, one
   winner. But the *fill* it produces is settled afterwards, and Phase 1 released the book
   lock in between. So a cancel could be adjudicated against a book that had already given
   up a resting order, while the fill that consumed it was still in flight: the cancel
   released the whole reservation, the fill then failed its reservation check, and the
   result was one settled half of a bilateral fill and 20 shares destroyed.

   In the distributed design this cannot happen, and that is the interesting part. The
   book is the *sole* producer of `orders.outcomes`, keyed by account, so a fill and the
   cancel verdict that follows it arrive in the order they were generated — the ordering
   is a property of the topic, not something anyone has to arrange. In-process there is no
   topic, and nothing supplied the guarantee. Phase 2 stands in for it by holding the book
   lock across matching *and* settlement, at the cost of serializing a symbol's matching
   with its ledger writes. Phase 3 deletes the lock and inherits the guarantee.

   **Generalization worth carrying forward:** every place a later phase gets an ordering
   guarantee from Kafka, an earlier phase needs an explicit mechanism for it. "It's ordered
   because it's in one process" is not true once one process does two things concurrently.

6. **Invariants over bilateral fills need an age dimension, or they are noise.** §8.2
   specifies `clearing_open_delta{age>5s}`, and the first implementation dropped the age
   part — so under live load the dashboard reported a violation every time a fill was
   mid-settlement, which is constantly. A fill is two transactions with no transaction
   spanning them; an unpaired half is the *normal* state between them. The check now
   separates **in-flight** (informational, expected non-zero under load) from **orphaned**
   (older than the settle window, a genuine alarm), and cross-account aggregates —
   clearing and share conservation — are computed over settled pairs only. This is finding
   #4's lesson arriving a second time, which suggests it is the general one.

7. **Opening positions must be purchased, not granted.** Seeding a market maker's
   inventory by moving shares in without moving cash leaves the position's cost basis
   nowhere in the ledger — it is a number the write path invents and stores, and no replay
   can reconstruct it. Modelling the seed as a purchase from `EXTERNAL` puts the basis in
   the cash leg where every other position's basis lives. The test that cost basis and
   realized P&L are reconstructible from postings alone does not pass without this, and
   that test is the real content of "the ledger is the source of truth".

### Found while building Phase 3 (splitting the matching engine)

8. **Two inbound topics cannot give a book one ordered input.** §7 lists `orders.accepted`
   and `orders.cancel_requested` as separate topics, and that quietly contradicts §5.4.
   With two topics the interleaving of an order and a cancel is whatever the two consumers
   happened to produce; on replay it can differ, the book linearizes them the other way,
   and a rebuild yields different executions than the ones clients were told about. They
   are merged into one **`orders.inbound`** topic keyed by symbol. One book, one stream,
   one order of events, one outcome.

   This is the same lesson as §0.7.5 arriving from the opposite direction: there, an
   ordering guarantee had to be *added* in-process because Kafka would later supply it;
   here, an ordering guarantee has to be *designed into the topic layout* because nothing
   else can supply it.

9. **Timestamps are deliberately absent from the wire, and that is not an oversight.** A
   fill event carries no clock reading. It cannot: the matching engine regenerates fills
   when it replays after a crash, and a wall-clock stamp applied at regeneration would
   differ from the original, breaking the byte-determinism that the whole recovery story
   rests on. Time is stamped where it is safe to stamp it — `transactions.created_at`, in
   the core, at settlement. The cost is that analytics has ingest-time rather than
   event-time, which is the correct trade for an explicitly eventually-consistent path.

10. **Only fills need a deterministic `event_id`; dispositions and cancel verdicts are
    idempotent by construction instead.** A fill moves money, so redelivery must be caught
    by a unique constraint. A disposition or a cancel outcome only *transitions a status*,
    and every such transition is guarded (`WHERE status NOT IN (terminal…)`), so applying
    it twice is already a no-op. Two different mechanisms, chosen per message type, and
    worth stating because "add an id to everything" would look tidier and buy nothing.

### Found while building Phases 4–6

11. **Foreign keys cannot cross a partition.** `fills` referenced `orders` for both the
    taker and the maker. The counterparty to a fill is, by construction, usually in another
    partition — that is what partitioning by account means — so its order row is in another
    database and no foreign key can reach it. This failed the first time a cross-partition
    fill settled. The general shape will recur: **a foreign key is a single-database
    construct, and any reference crossing a partition boundary must be enforced elsewhere
    or not at all.** Here it is not at all; the invariant that matters (both halves
    settled) is checked by the reconciler, which is the only thing that can see both.

12. **The venue belongs in the fill identity, and in the uniqueness constraint.** Each
    venue's book keeps its own `book_seq`, so `(shard, symbol, book_seq)` stops being
    unique the moment a symbol trades in two books. Two venues would mint the same
    identity for different executions and the ledger's dedup would discard a real fill as
    a duplicate. The identity was fixed first; the `fills` unique constraint had the same
    hole and had to follow. Note the failure mode it would have had in production: not a
    constraint error at the point of the bug, but a **stranded clearing position** hours
    later, pointing at nothing.

13. **Multiple venues are decorative unless an order can choose where it rests.** The
    router can sweep across venues when *taking*, but if every resting order lands at the
    primary venue then no liquidity ever accumulates anywhere else and there is nothing to
    sweep. `orders.venue` is a maker's preference for where to post; it never affects where
    a taker executes.

### Found by using it as a new user would

These came from opening an account, funding it, and trying to buy AAPL — one CLI command
at a time, the way a person actually would. Every phase's tests passed throughout. None of
them caught any of this, because every test ran inside a single process.

15. **A durable cursor into a non-durable stream loses data silently, and both halves look
    correct in isolation.** This is the one that mattered. Consumer offsets are durable and
    advance in the same transaction as the state they authorize — that is the exactly-once
    guarantee. The in-process log is not durable. Put them together and a second CLI
    invocation resumes at offset 1 against a log holding zero records, never reads the
    record it is waiting for, and the order it described is stuck forever with its
    reservation held. The user's money is simply gone, with every component behaving
    exactly as designed and nothing logging a warning.

    The fix is a Postgres-backed log (`internal/eventlog/pglog.go`), which is also a
    perfectly reasonable small deployment: one database, no broker, identical semantics.
    The general rule is worth carrying: **anything that persists a position into a stream
    requires the stream to persist at least as long.** The two are usually owned by
    different components, each of which is individually right.

16. **Fault injection must not force a different transport.** Chaos originally ran against
    the in-process log because that is where the duplicate-injection hook lived. Once the
    durable log became the default everywhere else, chaos was the one caller reading a
    fresh empty log while the database held offsets pointing into a different one —
    finding #15 all over again, in the one command whose whole job is to prove that cannot
    happen. Injection is now a hook on the interface, so choosing to inject faults never
    changes what is being tested.

17. **Reset is a whole-system operation.** `make reset` truncated the ledger but not the
    log, so recovery replayed events referring to accounts that no longer existed. This
    recurred three separate times — once for Kafka topics, once for the Postgres log, once
    for a stale snapshot — which is enough repetition to call it structural rather than
    careless. The log outlives the database by design; anything that clears one must clear
    the other.

18. **Tests must not share a database with the thing being used.** The test rig truncates
    every table on setup. Pointed at the same database the CLI uses, `go test` silently
    destroyed a live trading session. Obvious once it happens, invisible until then.

19. **A one-shot client must settle before it reads, and checkpoint before it exits.**
    Reading a book before draining the log reports an empty market that is not empty — a
    market order was rejected for want of a reference price while three price levels sat
    unconsumed. And a process that never snapshots leaves the next one replaying from
    offset zero, so the hundredth command is O(all history).

20. **"No reference price" is true and useless.** The engine was right to refuse a market
    order it could not collar, and the message said only that a value was missing. A person
    has to read the source to learn that a limit order works instead. An error on a path
    users hit first is documentation, whether or not it was written as any.

14. **An expired lease is not a lost lease.** Expiry only makes a partition *available*.
    A process that fenced itself the moment its own renewal was late would turn a GC pause
    into an outage; it keeps writing until someone actually takes the partition, and finds
    out then. Fencing is about preventing two writers, not about punishing one slow one.

## 1. Service inventory

Seven deployables. Risk remains a **package inside the trading core** — its check and the
fund reservation must be atomic, and a network boundary there buys a hop and a distributed
transaction in exchange for nothing.

| # | Service | Language | Sharded by | Owns |
|---|---------|----------|-----------|------|
| 1 | API Gateway | Go | stateless | auth, routing, fan-out reads, rate limiting |
| 2 | **Trading Core** | Go | `account_id` | accounts, cash, reservations, orders, positions, ledger |
| 3 | **Matching Engine** | Go | `symbol` | order books, market/limit matching, fills, venues |
| 4 | Market Data | Go | `symbol` | price simulation, conflating tick cache, tick firehose |
| 5 | **Market Makers** | Go | `symbol` | quoting strategy — *an ordinary gRPC client, not privileged* |
| 6 | Analytics | Go | stateless | ClickHouse ingestion, analytics query API |
| 7 | Chaos Controller | Go | — | fault injection, invariant verification (tooling, not prod) |

Supporting components (not separate services):
- **Outbox relay** — goroutine inside Trading Core tailing the outbox table into Kafka.
- **Reconciler** — job that queries every partition and computes the cross-partition
  invariants of §8.2. Cannot live inside a partition, because the invariants span them.
- **Risk package** — `internal/risk`, with a proto-defined interface so it *can* be split
  out later.

### Why Market Makers became a service (v2)

In v1, market makers were implied to live inside the matching shard. That silently
destroys replay determinism: a shard rebuilding its book from `orders.accepted` would
regenerate quotes from a fresh random walk and produce a different book, and therefore
different executions, than the ones clients were told about.

Making the market maker an ordinary client with an ordinary account fixes this by
construction — its quotes are orders, orders are logged, and the log is the truth. It also
delivers seam contract #3 for free: there is exactly one path into the book, and real
accounts in Part 2 use the same one.

**The cost is real and is budgeted.** MM quotes consume trading-core write capacity like
any other order. Mitigations, all config:
- Quote on *move*, not on a timer — refresh only when the reference price crosses a
  threshold (`MM_REQUOTE_BPS`, default 5).
- Rest wide, long-lived orders rather than cancel/replace churn.
- Spread MM accounts across partitions so they don't hot-spot one.

Budget MM traffic at ~20% of core write throughput and measure it separately in the load
report. A benchmark that hides MM cost inside the aggregate number is lying.

### 2.1 The two sharding domains, and the boundary between them

Trading Core is sharded by account (cash correctness is per-account). Matching is sharded
by symbol (book correctness is per-symbol). The Kafka hop between them re-keys.

- Per-account ordering is enforced **before** the boundary, in the trading core.
- Per-symbol price-time priority is enforced **after** the boundary, in the book.
- There is deliberately **no** guarantee that two orders from the same account for
  different symbols reach their books in submission order. They don't need one.
- **A fill crosses the boundary twice and lands in two different partitions.** This is the
  structural fact v1 missed, and §3.2 is the mechanism that makes it safe.

### 2.5 Ownership: leases, epochs, and the account row lock

Three distinct mechanisms, often conflated. Each does one job.

**(a) Routing — a hint.** The gateway computes `hash(account_id) % CORE_PARTITIONS` and
sends the RPC there. If it's wrong (stale membership), the core rejects with
`WRONG_PARTITION` and the gateway refreshes and retries. Routing is never load-bearing for
correctness.

**(b) The partition lease — the fence.** Each partition's database holds:

```sql
partition_leases(
  partition_id  int primary key,
  owner_id      uuid,           -- process instance
  epoch         bigint,         -- monotonically increasing, bumped on every acquisition
  expires_at    timestamptz
)
```

A core process acquires the lease by bumping `epoch` and setting `expires_at = now() +
LEASE_TTL` (10s), renewing every 2s. **Every write transaction asserts its epoch:**

```sql
SELECT epoch FROM partition_leases WHERE partition_id = $1;   -- must equal my_epoch
```

A mismatch aborts the transaction; the worker halts and re-acquires. Because the check and
the write are in the same transaction against the same database, a zombie process that
lost the lease during a network partition cannot commit — regardless of what Kafka or the
gateway believe.

This is the honest answer to "what stops two writers?" It is *not* that two membership
views agree. It is that Postgres arbitrates, and Postgres is also where the money is.

**(c) The account row lock — the serializer.** Within a partition, a pool of
`PARTITION_WORKERS` goroutines (default `2 × cores`) processes requests concurrently.
Every write transaction begins:

```sql
SELECT next_seq FROM accounts WHERE id = $1 FOR UPDATE;
```

This lock is the account's mutex. Two operations on the same account serialize; operations
on different accounts run fully concurrently. The same statement yields the per-account
sequence number (§3.1), so ordering and mutual exclusion come from one round trip.

**Consequence for throughput, stated plainly:** per-*account* write rate is capped at
roughly `1 / commit_latency` ≈ 250/s. Per-*partition* rate is bounded by Postgres group
commit, not by serial fsync — realistically 3–8k txn/s. This is why the load harness must
spread across many accounts; a benchmark that hammers one account measures the row lock
and nothing else, and should be reported separately as the per-account ceiling.

## 3. Data model

**Money is `int64` minor units (cents). Quantities are `int64` in units of 1e-6 shares.
No floats anywhere in the financial path, ever.**

The quantity scale is decided now, at zero cost, because changing it later is a migration
of every posting (v1 §17.4, resolved).

### 3.1 Core schema

```sql
-- identity and serialization point
accounts(
  id         uuid primary key,
  status     text,
  next_seq   bigint not null default 1,   -- ← the per-account clock (§9)
  created_at timestamptz
)

-- double-entry ledger: the source of truth
ledger_accounts(
  id            bigserial primary key,
  account_id    uuid,
  kind          enum('CASH','POSITION','RESERVED','FEES','CLEARING','EXTERNAL'),
  symbol        text null,               -- non-null iff kind IN ('POSITION','CLEARING')
  unique(account_id, kind, symbol)
)

transactions(
  id            bigserial primary key,
  account_id    uuid not null,
  account_seq   bigint not null,         -- ← replay watermark; allocated under row lock
  kind          enum('DEPOSIT','FILL_HALF','CANCEL_RELEASE','FEE','ADJUSTMENT'),
  event_id      uuid not null unique,    -- ← idempotency key; DETERMINISTIC (§5.3)
  order_id      uuid null,
  fill_id       uuid null,               -- ← pairs the two halves of one fill
  created_at    timestamptz,
  unique(account_id, account_seq)
)

postings(
  id            bigserial primary key,
  txn_id        bigint references transactions,
  ledger_acct   bigint references ledger_accounts,
  amount_minor  bigint                   -- signed
)
-- ledger_accounts carries a `unit`: 'USD' for money, the symbol for shares. See below.
```

**Balance is asserted per (transaction, unit), not per transaction.** A fill moves cash
*and* shares in the same transaction, and their amounts are denominated differently —
cents in one, share-millionths in the other. Summing them into a single figure and
demanding zero is arithmetic without meaning. Each unit of account balances separately:

```text
BUY 100 shares @ $150.00, 5bps fee
  unit USD:  CASH −1,500,750   FEES +750    CLEARING +1,500,000   → 0 ✓
  unit ACME: POSITION +100                  CLEARING −100         → 0 ✓
```

**The per-transaction balance invariant is a deferred constraint trigger, not a `CHECK`.**
A `CHECK` is evaluated per row and cannot see the other postings of the transaction. v1
said "enforced by constraint" and no such constraint is expressible.

```sql
CREATE CONSTRAINT TRIGGER postings_balance
  AFTER INSERT ON postings
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION assert_txn_balanced();
-- assert_txn_balanced: for each unit u, SUM(amount_minor) WHERE txn_id = NEW.txn_id
--                      AND ledger_accounts.unit = u must be 0
```

Firing at commit means intermediate states during a multi-posting insert are legal and the
final state is not negotiable.

```sql
-- projections, updated in the SAME transaction as the postings
positions(
  account_id, symbol,
  qty                bigint,             -- 1e-6 share units
  cost_basis_minor   bigint,
  realized_pnl_minor bigint,
  primary key(account_id, symbol)
)

-- order lifecycle
orders(
  id uuid primary key, account_id, symbol, side, type,
  qty bigint, limit_price_minor bigint null,
  tif enum('IOC','GTC'),                          -- §17.2 resolved
  ref_price_minor bigint null,                    -- stamped at accept; collar basis (§4.2)
  status enum(...), filled_qty bigint, avg_price_minor bigint,
  client_order_id text,
  unique(account_id, client_order_id),            -- ← client idempotency
  version int                                     -- optimistic concurrency
)

-- reservations now carry amounts, not just a state (v1 defect #10)
reservations(
  order_id       uuid primary key references orders,
  account_id     uuid not null,
  kind           enum('CASH','SHARES'),
  symbol         text null,
  reserved_minor bigint not null,        -- cash minor units, or qty for SHARES
  consumed_minor bigint not null default 0,
  released_minor bigint not null default 0,
  check (consumed_minor + released_minor <= reserved_minor),
  check (consumed_minor >= 0 and released_minor >= 0)
)
-- status is derived: ACTIVE iff consumed + released < reserved. Never stored.

-- fills, so both halves reference one object and the reconciler can pair them
fills(
  fill_id         uuid primary key,      -- deterministic (§5.3)
  symbol          text, shard_id int, book_seq bigint,
  price_minor     bigint, qty bigint,
  taker_order_id  uuid, maker_order_id uuid,
  unique(shard_id, symbol, book_seq)
)

-- plumbing
outbox(id bigserial primary key, topic, key, payload bytea, created_at, published_at null)
consumer_offsets(consumer_group, topic, partition, "offset", primary key(...))
snapshots(account_id, account_seq bigint, state bytea, created_at)   -- protobuf, not jsonb
partition_leases(...)                                               -- §2.5
```

**Buying power** is never a stored column:

```sql
cash_balance − SUM(reserved_minor − consumed_minor − released_minor)
               FROM reservations WHERE kind = 'CASH'
```

Derived, so it cannot drift.

### 3.2 The `CLEARING` ledger account — how a bilateral fill stays atomic

This is the central structural change in v2.

A fill involves two accounts, in two partitions, in two databases. There is no atomic
transaction spanning them and there will not be one. Instead, **the fill is decomposed
into two independent half-fills, each of which balances on its own**, against a clearing
counterparty:

```text
Fill: taker BUYs 100 AAPL @ $150.00 from maker, taker fee 5 bps, maker fee 0

  TAKER HALF  (partition of taker_account, one transaction)
    unit USD    CASH      −1,500,750
                FEES        +750
                CLEARING  +1,500,000        → 0 ✓
    unit AAPL   POSITION      +100
                CLEARING      −100          → 0 ✓

  MAKER HALF  (partition of maker_account, a DIFFERENT transaction, DIFFERENT database)
    unit USD    CASH      +1,500,000
                CLEARING  −1,500,000        → 0 ✓
    unit AAPL   POSITION      −100
                CLEARING      +100          → 0 ✓
```

Each half is locally atomic, locally balanced, and independently idempotent (distinct
`event_id`, shared `fill_id`).

**Global conservation becomes a pairing invariant.** Summing every `CLEARING` account
across every partition yields zero **once both halves of every fill have settled**. While a
half is in flight, it is legitimately non-zero. So the gauge is not "is it zero" but:

```text
clearing_open_delta{age > 5s}  — clearing imbalance attributable to fill halves
                                 whose sibling has not settled within 5 seconds
```

Zero under normal operation, non-zero exactly when a half-fill is stuck — which is the
condition you actually want to alarm on. This replaces v1's `money_conservation_delta`,
which was arithmetically incapable of being non-zero (§8.2).

**Corollary — no DLQ on the fill-apply path.** v1's failure matrix sent poison messages to
a DLQ with the offset advancing. On a half-fill, that permanently destroys the pairing and
therefore destroys money. A half-fill that cannot apply is a bug in this system, not a
malformed input from a stranger. It retries with backoff forever and pages a human. DLQs
remain for paths where nothing financial is at stake. (§10)

### 3.3 Order states

```text
CREATED → PENDING_RISK → REJECTED
                       → ACCEPTED → ROUTED → PARTIALLY_FILLED → FILLED
                                           → PENDING_CANCEL → CANCELLED
                                                            → FILLED        (race lost)
                                                            → PARTIALLY_FILLED
                                                              → CANCELLED   (remainder)
                                           → EXPIRED
```

`PENDING_CANCEL` is new in v2 and is not cosmetic. Without it, a core receiving a cancel
must either mark the order `CANCELLED` and release the reservation before the book has
agreed — after which an in-flight fill arrives for a cancelled order with no funds behind
it — or block the client until Kafka round-trips. Real venues expose pending-cancel; so
does `tradectl`.

`FAILED` remains deliberately absent. If an order can reach a terminal state called
"failed," you don't know whether money moved. Every path lands on REJECTED (nothing
happened), CANCELLED (reservation released), FILLED, or EXPIRED.

## 4. The hot path: order submission

One synchronous durable write. Everything after is async.

### 4.1 Accept

```text
1. Gateway  → validate, authenticate, route by hash(account_id) → partition P
2. Core[P]  → fetch ref_price from Market Data cache (point read, ≤ MAX_REF_PRICE_STALENESS)
              → if stale/absent and order is MARKET: REJECT(NO_REFERENCE_PRICE)
              → if stale/absent and order is LIMIT:  proceed (limit self-collars)
3. Core[P]  → BEGIN
                assert partition_leases.epoch = my_epoch          ← fencing (§2.5)
                SELECT next_seq FROM accounts WHERE id=$1 FOR UPDATE  ← serialize + clock
                check client_order_id not seen   (idempotent retry → return existing)
                risk.Check(account, order)       (in-process, reads own DB)
                INSERT reservation (amount per §4.2)
                INSERT order status=ACCEPTED, ref_price_minor=...
                UPDATE accounts SET next_seq = next_seq + 1
                INSERT outbox(topic=orders.accepted, key=symbol, payload=...)
              COMMIT
4. Core[P]  → ACK to client: {order_id, status: ACCEPTED}
5. relay    → outbox → Kafka   (async, at-least-once)
```

**Step 4 is the durability boundary.** Once committed, the order will reach exactly one
terminal state regardless of what crashes afterward. That claim rests on one transaction
rather than on a chain of RPCs succeeding.

Note that the `FOR UPDATE` in step 3 does double duty: it is the account's mutex *and* the
allocator of `account_seq`. One round trip, two guarantees, and the sequence it produces is
gap-free and commit-ordered — which is precisely what replay needs and what `bigserial`
cannot provide (§9).

### 4.2 Reservation sizing, and why cash cannot go negative

v1 said "INSERT reservation (cash for BUY)" without specifying the amount. For a market
order the fill price is unknown at accept time, so any under-reservation is a path to
negative cash — the single most damaging bug this system could have.

```text
BUY MARKET:  reserved = ceil(ref_price × qty × (1 + COLLAR_BPS/10_000)) + fee_estimate
BUY LIMIT:   reserved = limit_price × qty + fee_estimate
SELL (any):  reserved = qty  (shares, kind='SHARES')
```

`COLLAR_BPS` defaults to 500 (5%). The reservation is safe **only if the book refuses to
execute outside the collar**, so the collar is enforced in two places:

- **At accept**, to size the reservation.
- **In the book**, using `ref_price_minor` *carried on the order itself* — not re-queried.
  A market BUY will not execute above `ref_price × (1 + COLLAR_BPS)`. Any remainder that
  would cross the collar is cancelled, not filled. (§5.5)

Carrying the reference price in the order envelope rather than querying market data from
the matching engine is what keeps book replay deterministic — the book has no external
dependencies at all. It also makes every rejection auditable after the fact, because the
price the decision was based on is stored on the order.

**Therefore: realized fill cost ≤ reserved, always.** That is a property test, not a hope
(§13).

**This puts Market Data on the synchronous accept path** for market orders. v1's §6 implied
the transactional path never touches market data; that was true of tick *volume* and false
of point reads. The dependency is now explicit, bounded by a staleness limit, and has a
failure-matrix row (§10).

### 4.3 Apply a half-fill

```text
6. Matching → match, emit TWO events to orders.outcomes, key=account_id:
                {event_id: H(shard,symbol,book_seq,'TAKER'), fill_id, side: TAKER, ...}
                {event_id: H(shard,symbol,book_seq,'MAKER'), fill_id, side: MAKER, ...}
7. Core[P]  → BEGIN
                assert partition_leases.epoch = my_epoch
                SELECT next_seq FROM accounts WHERE id=$1 FOR UPDATE
                check transactions.event_id not seen   (dup → skip, commit offset)
                INSERT transaction(event_id, fill_id, account_seq)
                       + balanced postings incl. CLEARING leg   (§3.2)
                UPDATE positions
                UPDATE orders (filled_qty, avg_price, status)
                UPDATE reservations
                        SET consumed_minor += fill_qty × fill_price + fee,
                            released_minor += fill_qty × (reserved_per_unit − fill_price)
                UPDATE accounts SET next_seq = next_seq + 1
                UPDATE consumer_offsets                ← same txn as the state change
              COMMIT
```

**Offset-in-transaction is how you get effectively-exactly-once** without a dedup service.
State and offset advance atomically; a crash mid-way rolls back both, and reprocessing is
safe. The `event_id` unique constraint is belt-and-braces against a producer re-emitting
under a fresh offset — and it only works because `event_id` is deterministic (§5.3).

Note the reservation update: a limit BUY that fills below its limit price releases the
difference *per fill*, incrementally. The tri-state enum in v1 could not express this.

### 4.4 Latency budget (targets to validate, not to claim)

```text
gateway routing + auth              0.3 ms
ref price point read (cached)       0.2 ms   ← new in v2, market orders only
lease epoch assert (indexed read)   0.05 ms  ← new in v2
account row lock acquire            0.05 ms  (uncontended; per-account contention is the
                                              application's problem, not the system's)
risk check (in-process, DB)         0.5 ms
insert + commit (fsync)             2–4 ms   ← dominant cost
ack                                 0.2 ms
──────────────────────────────────────────
p50 submit-to-ack                    ~4 ms
p99 submit-to-ack                   ~25 ms

async: ack → both halves applied    10–40 ms (Kafka RTT + match + 2 × apply)
```

Throughput comes from concurrency across accounts, not from lowering this number. If you
later want a headline latency figure, hold hot account state in memory with a WAL behind it
(LMAX-style); serialized-writer-per-account is exactly the precondition that makes that
possible, which is why it is the first decision rather than a later optimization.

## 5. Matching engine

Sharded by symbol. Each shard owns a set of books; a book is never touched by two
goroutines. A book's entire input is one Kafka stream, which is what makes everything below
tractable.

### 5.1 Matching

```text
per symbol:
  bids: price-descending → FIFO queue of resting orders
  asks: price-ascending  → FIFO queue

MARKET order → walk the opposite side within the collar, consume levels, generate fills.
               Remainder beyond collar or beyond book depth → cancelled (market = IOC).
LIMIT  order → match what crosses, rest the remainder (GTC) or cancel it (IOC).
```

Resting orders are durable state: they survive restarts, need their own snapshot and
recovery path, and are sharded by symbol rather than by account. Budget real time for this.

### 5.2 Accept-path idempotency (v1 defect #9)

The outbox relay is at-least-once by design: if it crashes after producing but before
setting `published_at`, it republishes. v1's idempotency story covered the *fill* path via
`event_id` and left the *accept* path open. A republished `orders.accepted` inserts a
second resting order; the resulting fills are genuinely distinct events, so no downstream
constraint catches them.

Each book therefore keeps a **bounded dedup set of recently seen `order_id`s**, carried in
its snapshot:

- Live resting orders are already indexed by `order_id`, so those are free.
- Terminal orders go into a ring buffer of `BOOK_DEDUP_WINDOW` ids (default 1M ≈ 16 MB).
- Duplicates from the relay arrive within seconds of the original, so a window of minutes
  is ample.

**The stated assumption:** `BOOK_DEDUP_WINDOW` must exceed the maximum outbox relay lag. That
lag is monitored (`outbox_relay_lag_seconds`) and alarmed. A duplicate arriving after
eviction would double-insert — so the alarm is not decorative, and the window size and the
lag alarm threshold are documented together in the runbook.

Second line of defense: the core rejects an outcome for an `order_id` in a state that
cannot produce it, so a doubled resting order surfaces as a loud invariant violation rather
than a silent double fill.

### 5.3 Deterministic event identity (v1 defect #2 — the sharpest one)

v1's failure matrix said a fill lost to a crash is "re-derived on book rebuild" and
"idempotent via `event_id`." That is only true if the re-derived fill carries the *same*
`event_id`. A random UUID per fill makes the unique constraint useless and the fill applies
twice — creating money on a path the design advertised as safe.

Every book maintains `book_seq`, a monotonic counter incremented once per fill, part of its
snapshot state. Identity is a pure function of it:

```text
fill_id  = uuid_v5(NS_FILL,  shard_id ‖ symbol ‖ book_seq)
event_id = uuid_v5(NS_EVENT, shard_id ‖ symbol ‖ book_seq ‖ side)   -- side ∈ {TAKER,MAKER}
```

Deterministic under replay, unique by construction, and free of coordination. **Property
test:** replay a book from `orders.accepted` after a kill at an arbitrary point and assert
the emitted `event_id` sequence is byte-identical to the pre-crash one.

### 5.4 Recovery, and why it is deterministic

`orders.accepted` is the log. On restart a shard loads its latest snapshot (books + `book_seq`
+ dedup ring + consumed offset) and replays forward. Snapshot every N seconds or M events.

Determinism holds because the book has **no inputs other than its Kafka stream**:

- Market maker quotes arrive as ordinary orders on that stream (§1), so the price
  simulator's randomness is captured in the log rather than re-rolled at replay time.
- The collar reference price rides on each order (§4.2), so the book never queries market
  data.
- No `now()`, no `rand()`, no external calls in the apply path. Any non-determinism is
  captured *in the event* at write time.

v1 asserted deterministic rebuild while implying the simulator lived inside the shard.
Those two things cannot both be true; v2 keeps determinism and moves the simulator out.

### 5.5 Collar enforcement

The book will not execute a market order outside `ref_price_minor × (1 ± COLLAR_BPS)`,
using the value stamped on the order. Remainder is cancelled with reason
`COLLAR_BREACH`. This is what makes the reservation in §4.2 sufficient, and it is the only
thing standing between a thin book and negative cash.

### 5.6 Cancel, and the cancel/fill race (v1 §17.5, resolved)

Cancels reach the book via `orders.cancel_requested`, keyed by `symbol` — the topic v1
omitted, without which cancel had no transport at all.

The book is the single writer for its symbol and consumes cancels and new orders from one
merged, ordered input, so it **linearizes them**. The rule:

- Cancel sequenced before the crossing order → order cancelled, `CANCELLED`, full
  reservation released.
- Cancel sequenced after a full fill → `CANCEL_REJECTED(ALREADY_FILLED)`; core transitions
  `PENDING_CANCEL → FILLED`.
- Cancel sequenced after a partial fill → the unfilled remainder is cancelled; core
  transitions to `CANCELLED` and releases exactly `reserved − consumed − released`.

**The fill wins if it is sequenced first.** The core never releases a reservation on the
cancel *request* — only on the book's adjudication arriving via `orders.outcomes`. That is
what `PENDING_CANCEL` exists to represent.

### 5.7 Simulation knobs (after correctness is proven, behind config)

Slippage model (fixed bps, then size-dependent); synthetic latency distribution; liquidity
depth per symbol; multiple venues plus a simple smart order router (best price, then lowest
latency).

## 6. Market data

### 6.1 Why the backpressure problem disappears — and the condition attached

Routing 1M ticks/sec into portfolio state and then asking how to handle the backlog is a
self-inflicted problem: **portfolio state does not change when prices change.** Only
*unrealized P&L* changes, and that is derived:

```text
unrealized_pnl = qty × current_price − cost_basis
```

Computed at read time. Nobody queries their portfolio a million times a second.

**This is a consequence of current scope, not a law.** It holds while there is no margin
and no price-triggered order type. Stop orders, stop-limits, margin calls, or liquidation
would each make price a *trigger* for state change and would require a price→core path
with its own ordering and idempotency story. Adding any of them is therefore an
architectural change, not a feature. Recorded here so nobody adds stop orders casually.

### 6.2 Shape

```text
Market Simulator (random walk — the only non-deterministic component)
   │
   ├─► conflating in-memory cache (latest tick per symbol, older ticks DROPPED)
   │      ├─► gRPC point reads → Trading Core (ref price at accept, §4.2)
   │      └─► gRPC streaming   → Market Makers (quoting input)
   │
   └─► Kafka market.ticks (raw, key=symbol) ─► ClickHouse (batched, 1s / 10k rows)
```

Conflation is what real market data infrastructure does: a superseded tick has no value, so
dropping it is correct, not lossy.

Note where the simulator sits: **outside the replay boundary**. It influences the system only
by causing market makers to submit orders, and those orders are logged. Replaying the log
reproduces the book exactly, even though re-running the simulator would not reproduce the
prices. That separation is the whole reason §5.4's determinism claim survives.

## 7. Kafka topics

| Topic | Key | Partitions | Retention | Producer → Consumer |
|---|---|---|---|---|
| `orders.accepted` | `symbol` | M | 7d | Core → Matching |
| `orders.cancel_requested` | `symbol` | M | 7d | Core → Matching |
| `orders.outcomes` | `account_id` | N | 7d | Matching → Core |
| `orders.events` | `order_id` | N | 30d | Core → Analytics |
| `ledger.postings` | `account_id` | N | ∞ | Core → Analytics |
| `market.ticks` | `symbol` | M | 24h | MarketData → Analytics |
| `*.dlq` | — | 1 | 30d | non-financial paths only (§10) |

Changes from v1: `orders.cancel_requested` added (cancel had no transport);
`orders.executed` renamed `orders.outcomes` because it now carries `FILL_HALF`,
`CANCELLED`, `CANCEL_REJECTED`, and `EXPIRED` — one ordered outcome stream per account is
simpler to reason about than several, and the core's apply loop is a single switch.

**Every fill produces two messages on `orders.outcomes`**, keyed by the two different
accounts, landing in two different partitions. This is the visible consequence of §3.2 and
the thing to point at when explaining why clearing accounts exist.

Partition counts N and M are set to the *maximum* intended worker count from day one (32).
Kafka partitions are cheap; repartitioning a live keyed topic is not.

The symbol→shard function must be identical to Kafka's partitioner for `orders.accepted`,
or a shard will consume orders for books it does not own. Use an explicit
`murmur2(symbol) % M` on both sides rather than relying on client-library defaults matching.

**Schema versioning is not optional** given a replayable immutable history. Protobuf +
Confluent Schema Registry with `BACKWARD` compatibility enforced in CI. Every envelope
carries `schema_version`; a field added in month three reads as a proto3 default when
replaying month-one events.

## 8. Consistency guarantees

### 8.1 What is guaranteed

1. **Durability.** An order acknowledged `ACCEPTED` is durable and will reach exactly one
   terminal state (REJECTED / CANCELLED / FILLED / EXPIRED).
2. **Per-account ordering.** Operations on one account's cash and positions are applied in
   submission order, enforced by the account row lock and `account_seq`.
3. **Per-symbol ordering.** Orders reaching a book are matched in price-time priority.
4. **No cross-account ordering.** Explicitly not guaranteed. Not needed.
5. **Local atomicity.** Every financial state change is one balanced double-entry
   transaction: `SUM(postings.amount_minor) = 0` per `txn_id`, enforced by deferred
   constraint trigger.
6. **Bilateral atomicity is eventual, not immediate.** A fill is two locally-atomic halves
   in two partitions. Between them the system holds an open clearing position. This is a
   *weaker* guarantee than v1 claimed, and it is the true one. It is bounded: `clearing_open_delta{age>5s}`
   alarms, and the fill-apply path never discards a message (§10).
7. **Strong consistency of positions and cash with the ledger.** Same database, same
   transaction. Divergence is structurally impossible, not merely unlikely.
8. **Effectively-exactly-once application.** Offset advances in the same transaction as the
   state change; `transactions.event_id` is unique *and deterministic*. Kafka delivers
   at-least-once; the database makes it once.
9. **No writes from a fenced process.** A core that lost its partition lease cannot commit,
   because the epoch assertion shares a transaction with the write.
10. **Eventual consistency for analytics.** ClickHouse lags ≤ 5s p99. Never read for a
    financial decision.

Guarantee 6 is the one to lead with when someone asks a hard question. Volunteering the
place where atomicity is eventual, along with the bound and the detector, is more
convincing than claiming it everywhere.

### 8.2 Invariants that actually detect something

v1 listed three checks. Two were tautologies and none could execute as written, because
Postgres-per-partition means these are not single-database queries.

- ~~`SELECT SUM(amount_minor) FROM postings … = 0`~~ — follows mathematically from the
  per-transaction balance constraint. Cannot be non-zero unless the trigger is broken.
- ~~positions vs. ledger projection~~ — written in the same transaction; v1 conceded this in
  prose and then put it on the dashboard anyway.

Demoted, not deleted: both remain as **corruption checks** (they catch a broken trigger,
a bad migration, or manual `UPDATE`s in production), labeled as such, off the headline row.

The real invariants span partitions and are computed by the **reconciler**, which queries
every partition on a 1s cycle:

```text
clearing_open_delta{age>5s}
    Σ over partitions of CLEARING balances, restricted to fill_ids whose sibling half has
    not settled within 5s.
    Non-zero ⟺ a half-fill is stuck. This is the money-conservation gauge.

share_conservation_delta{symbol}
    Σ over partitions of positions.qty for a symbol, minus shares seeded via EXTERNAL.
    Non-zero ⟺ shares were created or destroyed. Non-tautological because the terms come
    from different databases.

cash_conservation_delta
    Σ CASH + Σ RESERVED + Σ FEES + Σ CLEARING across partitions, minus Σ external deposits.
    Non-zero ⟺ money entered or left the system without a deposit.

unbalanced_txn_count            (per partition; trigger backstop)
position_ledger_mismatch_count  (per partition; corruption check)
orphaned_fill_half_count{age>5s}
    fills with exactly one settled half. Overlaps clearing_open_delta by design —
    two independent detectors of the same fault class, derived from different tables.
```

Each is a Prometheus gauge; the first three go in the top row of the dashboard, large.
During a chaos demo they are the story.

### 8.3 On reconciliation

Within a partition, reconciliation cannot detect drift between ledger and positions,
because they are written in one transaction — there is no drift to find. It detects
**corruption, application bugs, and manual intervention**.

Across partitions there is genuine reconciliation to do, and it is continuous rather than
nightly: pairing fill halves, conserving shares per symbol, conserving cash against
deposits. That is what the reconciler is for, and it is the honest version of the
"reconciliation service" in the original design.

## 9. Replay and snapshots

### 9.1 The watermark (v1 defect #7)

v1 replayed `postings WHERE seq > snapshot.seq`, against a `seq` column that did not exist.
The obvious substitute is fatal:

> **`bigserial` must never be used as a replay watermark.** Sequence values are allocated
> before commit, so a transaction holding id 500 can commit *after* one holding id 700.
> Snapshot at watermark 700 and record 500 is skipped forever. Worse, the acceptance test
> would still pass, because both replay paths read the same broken ordering.

The correct watermark is `transactions.account_seq`, allocated from `accounts.next_seq`
under the account's row lock (§2.5c). Because it is allocated *inside* the serialized
critical section, it is gap-free and commit-ordered by construction.

```text
snapshot(account_id, account_seq) every 10k events or 5 min
recover(account) = load latest snapshot
                 → replay transactions WHERE account_seq > snapshot.account_seq
                   ORDER BY account_seq
```

The same field also gives per-account ordering (§8.1.2) and a natural cursor for
`SubscribeFills` resumption. One mechanism, three uses.

### 9.2 Snapshot encoding

`snapshots.state` is **canonical protobuf `bytea`**, not `jsonb`. The acceptance test
demands byte-identical comparison, and `jsonb` normalizes key order and numeric
representation — it would make the test either flaky or vacuous depending on the driver.
Deterministic serialization: fields in tag order, maps sorted by key, no unknown-field
retention.

### 9.3 The test that matters

Full replay from genesis and snapshot-then-replay must produce byte-identical state.
Property test it. That is a stronger demonstration than replay alone, because it proves the
snapshot is not lying.

Extended in v2 to the matching engine: replay of a book from `orders.accepted` must produce
a byte-identical book *and* an identical `event_id` sequence (§5.3). Without the second
half, a rebuild that produces the right positions via different fill identities would still
double-apply downstream.

Replay must be deterministic: no `now()`, no random, no external calls in any apply path.
All non-determinism is captured *in* the event at write time.

## 10. Failure matrix

| Failure | Behavior | Recovery |
|---|---|---|
| Gateway dies | client retries; `client_order_id` dedupes | stateless restart |
| Trading Core partition dies | that partition's accounts unavailable; **others unaffected** | lease expires (10s), new owner bumps epoch, resumes from `consumer_offsets`, republishes outbox rows with `published_at IS NULL` |
| **Core partitioned from network but alive (zombie)** | lease expires; **its transactions abort on the epoch assertion** | rejoins as a follower, re-acquires or exits |
| Core dies after COMMIT, before relay | order is durable; relay republishes on restart | at-least-once → book dedup window (§5.2) |
| Matching shard dies | orders queue in Kafka; no loss | rebuild books from snapshot + `orders.accepted`; deterministic (§5.4) |
| Matching dies after fill, before produce | fill re-derived on rebuild with the **same** `event_id` | dedup at core; no double-apply (§5.3) |
| **One half-fill applies, sibling partition down** | clearing position open; `clearing_open_delta` non-zero after 5s | sibling recovers and applies; **never discarded** |
| **Market Data dies / cache stale** | **market orders rejected** (`NO_REFERENCE_PRICE`); **limit orders still accepted** (self-collaring) | restart; cache warms from simulator |
| Postgres restart | in-flight txns roll back; core blocks and retries | pool reconnect, exponential backoff, lease re-assert |
| Kafka broker down | outbox accumulates; submissions still ACK | relay drains backlog on recovery |
| Duplicate outcome delivery | `event_id` unique violation → skip, commit offset | no-op |
| Duplicate `orders.accepted` | book dedup window rejects | no-op; alarms if lag > window |
| Consumer lag growth | monitored; conflated topics shed load naturally | scale consumers ≤ partition count |
| Poison message, **non-financial path** | 3 retries → DLQ, offset advances | operator replay after fix |
| Poison message, **fill-apply path** | **no DLQ.** Retry with backoff indefinitely; page | human fix; the message is money |

The last row is a v2 correction. v1 applied a uniform DLQ policy, which on a half-fill
means advancing past money. A half-fill that will not apply is a bug in code we wrote, not
hostile input, and the correct response to "our code is wrong about money" is to stop and
shout, not to skip and continue.

The availability story: partition P failing takes down only the accounts hashed to P. That
is a property of the partitioning, not a claim.

## 11. Scaling

```text
core write rate required
  = order accepts
  + 2 × fills                 ← both halves land in the core (§3.2)
  + MM quote submissions      ← ~20% budget (§1)
  + cancels

throughput ≈ min(
   partitions × per-partition commit rate,   ← Postgres group-commit bound, 3–8k txn/s
   symbol shards × per-book match rate,      ← CPU bound, very high
   kafka partition throughput
)
```

v1's model counted only accepts. Since every fill produces two core transactions and market
makers submit real orders, the core does meaningfully more work per unit of *client*
throughput than v1 implied — roughly 3–4× at high fill rates. Reporting client orders/sec
without this arithmetic would overstate headroom.

Two ceilings, and they are different:
- **Per-account:** ~250 ops/sec, set by commit latency under the row lock. Not a bug; no
  real account trades that fast. Report it separately as a known limit.
- **Per-partition:** group-commit bound. This is the number that scales.

Measure the curve explicitly: `1 → 2 → 4 → 8 → 16 partitions`. Expect near-linear until
shared I/O saturates, then flat. **Finding and explaining the knee is the valuable result** —
a linear graph to infinity means you did not push hard enough. Give each partition its own
database (not merely its own tablespace) to keep the curve linear longer.

## 12. Observability

Every service: Prometheus metrics, structured JSON logs with `trace_id`, OpenTelemetry
traces spanning gateway → core → Kafka → matching → core (both halves).

```text

Kafka:      consumer lag per topic/partition, produce latency
DB:         txn duration, pool saturation, lock waits, account-lock contention
Leases:     lease age, epoch bumps/min, epoch-assertion failures   ← should be ~0
Outbox:     outbox_relay_lag_seconds                               ← gates §5.2's window
Business:   orders/sec, fills/sec, rejection rate by reason (incl. COLLAR_BREACH,
            NO_REFERENCE_PRICE), MM order share
INVARIANTS: clearing_open_delta{age>5s}      ← top row
            share_conservation_delta          ← top row
            cash_conservation_delta           ← top row
            orphaned_fill_half_count{age>5s}
            unbalanced_txn_count, position_ledger_mismatch_count   (corruption checks)
```

happening and being correctly fenced — interesting either way).

## 13. Testing strategy

**Unit** — matching logic, risk rules, posting generation, reservation arithmetic.
Table-driven.

**Property-based** — where the real bugs live:
- Any sequence of deposits/orders/fills/cancels ⟹ money is conserved across all partitions.
- Any interleaving of concurrent orders ⟹ cash never goes negative.
- **Realized fill cost ≤ reserved amount, for every order, always.** (§4.2)
- `Replay(events) == Replay(snapshot + tail)`, byte-identical.
- **Book replay produces an identical `event_id` sequence.** (§5.3)
- Any duplicated subsequence of events ⟹ identical final state.
- **Every fill has exactly two settled halves, and their clearing legs sum to zero.**
- Cancel/fill race: for any interleaving, the reservation ends fully consumed or fully
  released, never partially stranded.

**Integration** — testcontainers: Postgres + Kafka. Full path submit → match → both halves →
positions → ledger.

**Distributed failure** — the chaos controller, run as a CI job, not a manual demo.

**Load** — 1k → 10k → 100k orders/sec. Report the ceiling and the bottleneck, honestly, with
the MM share broken out.

### 13.1 The oracle problem

v1's exit criteria counted duplicates from the ledger under test — self-referential; a bug
that double-applies would likely also miscount. The harness therefore maintains its own
external ledger:

- Set of submitted `client_order_id`s with submission timestamps.
- Terminal states pulled from partitions at the end, joined against that set.
- `Lost` = submitted with no terminal state. `Duplicated` = terminal state count exceeding
  submission count, **or** any `fill_id` with a half-count ≠ 2.

Independent of the invariant machinery it is checking.

### 13.2 Chaos controller

```bash
chaos kill-service trading-core --partition 3
chaos kill-service matching --shard 7 --during-fill
chaos delay-service matching 500ms
chaos duplicate-events orders.outcomes 5%
chaos duplicate-outbox --rate 5%              # exercises the accept-path dedup (§5.2)
chaos partition-network core matching --duration 30s
chaos partition-network core postgres --partition 2   # exercises the lease fence
chaos kill-partition-sibling --during-fill     # strands a half-fill on purpose
chaos restart-kafka --broker 2
chaos kill-postgres --partition 1
chaos stale-market-data --duration 30s         # exercises market-order rejection
```

Every run ends with the same verification block:

```text

Orders terminal:           1,000,000
```

## 14. Build order

Do **not** stand up seven services before one order has executed end to end.

**Phase 1 — Vertical slice with a real book (monolith, no Kafka).**
One Go binary, one Postgres. Deposit → limit orders resting in a real in-process
price-time-priority book → market BUY crossing them → two half-fills applied in the same
process → positions + balanced postings with `CLEARING` and `FEES` legs. One hardcoded
market maker resting quotes. Money-conservation and cost-≤-reservation property tests
passing.

> The book is built here, not later. In Phase 1 it is a single-threaded in-memory data
> structure with no network around it — the cheapest it will ever be. v1 deferred it to
> Phase 5 behind a "synchronous fill," which is the stub seam contract #3 forbids, and
> which would have to be torn out under deadline.

Fees and clearing accounts exist from the first commit. Retrofitting either into a
double-entry system means rewriting every posting (§17.3).

**Phase 2 — Ledger hardening.**
Reservations with amounts, collars, buying power, SELL path, realized/unrealized P&L,
cancel with `PENDING_CANCEL` and release. `account_seq`, replay from event log, protobuf
snapshots. Invariant checks as metrics.

**Phase 3 — Split the matching engine.**
Extract to its own service. Kafka for `orders.accepted`, `orders.cancel_requested`,
`orders.outcomes`. Transactional outbox, offset-in-transaction, deterministic `event_id`,
book dedup window, book snapshot/recovery. Duplicates and crashes are now possible — prove
idempotency holds, including `chaos duplicate-outbox`.

**Phase 4 — Partition the core.**
Hash routing in the gateway, N partitions, worker pool per partition, account row lock,
**partition leases with epoch fencing**. Cross-partition reconciler, since fills now
genuinely span partitions. Kill one partition and show others keep trading. Plot the
scaling curve.

**Phase 5 — Market makers, depth, and venues.**
Market makers extracted to their own service as ordinary gRPC clients. Multiple symbols,
realistic depth, slippage, multiple venues, smart order router. IOC/GTC.

**Phase 6 — Harness, analytics, and the demo.**
Chaos controller in CI, ClickHouse ingestion and analytics queries, Grafana dashboard with
invariant gauges, load test report, `tradectl` CLI, `SubscribeFills` streaming RPC.

Gate each phase on: *the invariant tests still pass under chaos.* If they don't, don't
proceed.

> Phase ordering changed from v1: the real book moved from Phase 5 to Phase 1, and market
> makers became a Phase 5 *extraction* rather than a Phase 5 *construction*. The riskiest
> component now gets built when it is cheapest and gets exercised by every subsequent
> phase.

### Part 1 is done when

```text
□ 1M synthetic orders submitted under active chaos
□ Orders terminal: 1,000,000   Lost: 0   Duplicated: 0
□ Every fill has exactly 2 settled halves; orphaned halves: 0
□ Unbalanced txns: 0   Clearing open Δ: $0.00   Share Δ: 0   Cash Δ: $0.00
□ Realized cost ≤ reserved on every order (property test, 10^6 cases)
□ Scaling curve plotted 1→16 partitions, knee identified and explained
□ replay(genesis) == replay(snapshot + tail), byte-identical, core AND books
□ Book replay reproduces the identical event_id sequence
□ Kill any single partition: others keep trading, killed one recovers < 5s
□ Network-partition a core from its Postgres: zero writes from the fenced process
□ Documented p50/p95/p99 with the bottleneck named and MM load broken out
```

## 15. Tech decisions, stated plainly

| Choice | Rationale |
|---|---|
| Go everywhere | goroutines suit partitioned workers; one toolchain; fast |
| gRPC + protobuf | typed contracts, and the schemas double as Kafka envelopes |
| Postgres per partition | fsync is the throughput ceiling; don't share it. Also the lease arbiter |
| Row lock as account mutex | the serializer and the sequence allocator in one round trip |
| Lease + epoch over consensus | one fencing check, no Raft, no extra dependency |
| Clearing accounts over 2PC | a bilateral fill becomes two locally-atomic halves plus a pairing invariant |
| Kafka | keyed partitioning maps exactly onto the sharding model |
| Deterministic UUIDv5 event ids | the only thing that makes crash-derived fills idempotent |
| ClickHouse | genuine columnar analytics workload, fed in batches |
| int64 minor units, 1e-6 qty | floats in ledgers are latent bugs; scale decided before it's a migration |
| Outbox over 2PC | 2PC across Postgres and Kafka is not worth it and mostly doesn't work |
| Protobuf snapshots over jsonb | byte-identical comparison must mean something |
| Docker Compose → k8s | local first; AWS only once the invariants hold under chaos locally |

## 16. Deliberately out of scope

**Out of Part 1, deferred to Part 2:** auth, sessions, user accounts, rate limiting, web UI,
WebSocket transport, public deployment, leaderboards.

**Out of both parts, permanently:** real brokerage integration, live/licensed market data
feeds (simulated prices sidestep exchange redistribution agreements entirely — real tickers
as labels only), crypto, technical-analysis indicators, trading bots, 50 instruments,
mobile apps, a frontend framework.

**Out of scope with a stated architectural reason** (these are not merely unbuilt — they
would each break a guarantee above, so adding one is a design change):
- **Margin and leverage** — breaks §6.1; price becomes a trigger for state change.
- **Stop / stop-limit orders** — same; requires a price→core path with its own ordering
  and idempotency story.
- **FOK / all-or-none** — requires the book to reason about a whole order atomically across
  price levels, complicating §5.6's linearization.
- **Partition rebalancing** — see §17.1.

## 17. Resolved decisions

v1 left these open "until Phase 3." Each becomes expensive at a specific moment, and three
of them become expensive in Phase 1. All are decided.

**17.1 Partition rebalancing — no.** Fixed hash, `CORE_PARTITIONS = 16` from genesis,
never changed for a live deployment. Config exists so the playground can run 2 and the
benchmark 16, but a given cluster's value is set at genesis and is immutable. Consistent
hashing is explicitly out of scope. The documented migration path, if ever needed: drain
partition → snapshot → copy → bump epoch → resume, offline, per partition.
*Cost of deciding later: an account's ledger history spans two databases and replay breaks.*

**17.2 TIF — IOC and GTC only.** Market orders are implicitly IOC. Limit orders default
GTC. No DAY (requires a session clock and an expiry sweeper). No FOK (requires all-or-none
matching across levels; see §16).
*Cost of deciding later: state-machine growth, which is where the cancel/fill race lives.*

**17.3 Fees — modeled, from Phase 1.** A `FEES` ledger account per account, taker fee
`TAKER_FEE_BPS` (default 5), maker fee zero. Fee headroom is included in every BUY
reservation (§4.2).
*Cost of deciding later: v1 said it correctly — retrofitting fees into a double-entry
system means rewriting every posting. That is a Phase 1 decision masquerading as a Phase 3
one.*

**17.4 Fractional shares — `int64` in units of 1e-6 shares.** Decided now at zero cost.
*Cost of deciding later: a migration of every posting and every position.*

**17.5 Cancel/fill race — resolved in §5.6.** The book linearizes cancels and orders from
one input stream. The fill wins if sequenced first. The core holds `PENDING_CANCEL` and
releases the reservation only on the book's adjudication.
*Cost of deciding later: this one had no transport at all in v1 — no Kafka topic, no order
state. It was not a decision awaiting a call; it was a hole.*

## 18. What to say when someone attacks this

The three questions a knowledgeable reviewer will ask, and the honest answers:

**"A fill involves two accounts in two databases. Where is your distributed transaction?"**
There isn't one. The fill is two locally-atomic halves, each balanced against a clearing
counterparty. Global conservation is a pairing invariant with a five-second detection
window, the fill-apply path never discards a message, and `clearing_open_delta` is on the
dashboard precisely because this is the seam.

**"Kafka rebalancing doesn't fence anything. What stops two cores writing the same
account?"** The lease epoch, asserted inside the write transaction against the same
Postgres that holds the money. Routing and consumer-group assignment are hints; Postgres
arbitrates. `epoch_assertion_failures` is a metric, and it is occasionally non-zero, which
means it is working.

**"You said replay is deterministic, but you have a random price simulator."** The
simulator is outside the replay boundary. It only influences the system by causing market
makers — ordinary clients with ordinary accounts — to submit orders, and those orders are
in the log. Replaying the log rebuilds the book exactly; re-running the simulator would
not, and never needs to.

Each of these was a real defect in v1. Being able to name where a design *was* wrong and
what specifically changed is worth more than a document that was never wrong on paper.
