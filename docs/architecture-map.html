The path an order takes

One order, top to bottom. The heavy rule is the durability boundary: everything above it happens in a single Postgres transaction and the client is told ACCEPTED there. Everything below is driven by the log and can crash, restart, and repeat without costing anything.

synchronous · one durable transaction asynchronous · driven by the log

Why a fill needs two transactions

A fill has two counterparties, and accounts are sharded across partitions — so the two sides usually live in different databases. There is no transaction that spans them, which is the single most consequential fact in the design.

The one file to read first. If you only open one, make it internal/engine/outcomes.go. It holds the settlement path, the offset-in-transaction commit, the double-entry legs, and the reservation arithmetic — every claim the system makes about money is enforced somewhere in it.

The trap this map exists partly to warn about. memlog.go is not durable. Consumer offsets are. A durable cursor into a non-durable stream loses records silently — it stranded a live order and its reservation during testing. Use pglog.go or kafkalog.go for anything whose state outlives one process.

Known gap worth seeing on the map. Every test above drives Drain() — pump until quiet. Production drives Run() — background loops. That asymmetry is why the bugs found by using the CLI by hand were invisible to 2,700 lines of tests.
